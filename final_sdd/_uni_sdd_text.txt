1.4 Architectural Design
The system follows the decoupled, multi-tier architecture described in the SRS. The browser
communicates with the Next.js application hosted on Vercel. Tenant middleware resolves the
hostname to a store slug and applies route guards. Next.js communicates with Supabase for
authentication and persistent data. It calls the FastAPI analytics service for feasibility analysis.
The analytics service retrieves external data, engineers features and runs the versioned XGBoost
model. The application uses a multi-provider AI router to generate structured advice. Store
assets are held in Supabase Storage. Domain provisioning is delegated to the Vercel Domains
API.
Figure 1.2 presents the main runtime components and their connections. The web tier owns
user-facing workflows and tenant resolution. The analytics tier owns data aggregation, feature
engineering, scoring and risk calculation. The data tier stores profiles, reports, stores, products
and orders under RLS. External services are isolated behind API clients or provider adapters.
This arrangement keeps machine-learning processing separate from request handling in the web
tier.

1.7 Data Design
1.7.1 Database Architecture
The system uses one shared PostgreSQL database through Supabase. Tenant records are associ-
ated with an owner or store identifier. Row-Level Security is enabled with default-deny access and
is forced on tenant tables. Administrative checks use a security-definer helper to avoid recursive
profile-policy evaluation. Guest orders are accepted only through a validated server-side function;
anonymous users do not receive a direct insert policy on order tables. Money values are stored as
integer PKR using BIGINT, as specified in the SRS.
1.7.2 Entity Relationship Diagram
Figure 1.14 shows the logical entities and their relationships. Supabase Auth users map one-to-
one to profiles. A profile can own multiple feasibility reports and stores. A feasibility report may
form the basis of a store. A store contains multiple products and receives multiple orders. Each
order contains one or more order items. AI calls are logged against an owner when applicable.
The rent cache is keyed by a unique city and area pair and is consulted by the analysis service.

2.7.3 Navigation Flow
The navigation follows the actor journeys described in the SRS. An owner signs in, completes
the idea wizard, reviews the feasibility dashboard and advisory, then proceeds to the theme
configurator and store publishing. The owner dashboard provides product and order management.
A guest enters a tenant URL, browses products, checks out using COD and receives confirmation.
An administrator enters the separate administration area after role verification.
2.7.4 Responsiveness and Performance
The frontend is specified as a responsive web application for modern desktop and mobile browsers.
Analysis is performed by a separate FastAPI service so that model inference does not need to
run in the browser. Cache-first data retrieval reduces repeated external requests. The SRS sets
a target of a feasibility result within 15 seconds at the 90th percentile for typical warm-cache
requests. It also sets a target of publishing a store within three minutes after the theme wizard
is completed. These are acceptance targets; measured results must be collected during testing
before they are reported as achieved.
